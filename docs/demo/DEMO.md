# Текст для демо та захисту — навичка `wikipedia-interest`

Мета: за 7–10 хвилин показати, що навичка вирішує задачу із завдання, чому їй можна довіряти, і як це
перевірено. Далі — заготовки відповідей на питання. Курсивом — що показати на екрані.

---

## 1. Вступ (1 хвилина)

Командам B2C-продуктів треба вирішувати, у що вкладатись далі: який курс додати, яку тему розкрити,
якою мовою запускатись. Один із дешевих і публічних сигналів — статистика переглядів Wikipedia за
мовними розділами. Проблема в тому, що сирі перегляди брешуть: англійський розділ завжди «виграє»
через розмір, новинні сплески виглядають як тренд, боти рахуються як люди, а поточний місяць неповний.

Я побудував навичку для AI-агента у форматі Agent Skills, яка бере запит засновника природною мовою —
«чи росте інтерес до астрономії в україномовній Wikipedia і наскільки цьому можна довіряти?» — і за 1–3
виклики інструментів дає відповідь із числами, рівнем довіри, графіком і односторінковим PDF. Головне
слово тут — **довіра**: навичка не просто рахує ріст, а каже, наскільки цей ріст стійкий і що його
пояснює.

*Показати: `wikipedia-interest/SKILL.md` (перші 30 рядків) і дерево каталогу.*

## 2. Що це технічно (1 хвилина)

- Самостійна навичка: `SKILL.md` (≈120 рядків інструкцій для агента) + власний Python-код (`wiki_interest/`),
  який виконує всю змістовну роботу; агент лише викликає команди й читає коротке резюме.
- Шість команд: `resolve`, `analyze`, `verify`, `compare`, `discover`, `report`.
- Відтворюване середовище: `uv` + `uv.lock`, без системних залежностей (PDF — reportlab + шрифт із matplotlib).
- Джерела: Wikimedia Pageviews API (per-article, aggregate, top), Wikidata (зіставлення тем зі статтями),
  MediaWiki API (редиректи, пошук, простори назв).
- Кеш SQLite: закриті місяці — назавжди, повторні й уточнюючі запити — секунди.

## 3. Демо-сценарій (4–5 хвилин)

Усі команди — з каталогу `wikipedia-interest/`. У кожній є готовий вивід у `examples/`, якщо мережа підведе.

### 3.1 Запит із завдання №2 — астрономія в uk
```bash
uv run scripts/wiki_interest.py analyze --topic "астрономія" --langs uk --months 36 --out runs/astro-uk
```
*Показати резюме.* Що казати:
- «6.3 перегляди на мільйон переглядів розділу — це частка уваги, а не сирі перегляди».
- «Ріст −47 %/рік з вирізаними піками; довіра **high**: покриття 100 %, піків 0 %, монотонний тренд».
- «Checks: сильна сезонність (амплітуда ≈3×) — вересневі шкільні піки, і кожен наступний нижчий:
  9857 → 4687 → 1642 переглядів. Це реальне падіння, не артефакт».
- «Відповідь для засновника: інтерес до теми на Wikipedia падає — перш ніж інвестувати в курс, перевірити,
  чи не перейшов попит в інші канали».

### 3.2 «А наскільки цьому можна довіряти?» — `verify`
```bash
uv run scripts/wiki_interest.py verify --run runs/astro-uk
```
*Показати вердикт.* Що казати:
- «П'ять незалежних перевірок: десктоп проти мобільних, люди проти всього трафіку (частка ботів), вікно
  без перших/останніх трьох місяців, контрольна перевірка одного місяця напряму з API повз кеш, і базова
  лінія всього розділу».
- «Для астрономії: падіння видно і на десктопі (−41 %), і на мобільних (−52 %), боти 27 % — норма для
  Wikipedia, контрольна перевірка збігається. Вердикт mixed через розрив між пристроями, але напрям стійкий».
- Найсильніший приклад: `examples/03-english-multi/verify.md` — стаття «Englische Sprache» (de), яку
  `analyze` позначив low confidence, у `verify` показує **74.8 % не-людського трафіку**. Саме так навичка
  допомагає агенту перевіряти висновки, а не лише робити їх.

### 3.3 Запит №1 — інтервальне голодування pl vs cs
```bash
uv run scripts/wiki_interest.py resolve --topic "intermittent fasting" --langs pl,cs
uv run scripts/wiki_interest.py analyze --topic "intermittent fasting" --langs pl,cs --months 24 --out runs/if
```
Що казати: «У польській Wikipedia статті немає. Навичка не вгадує назву — показує кандидатів пошуку і
каже агенту: відсутність статті ≠ відсутність інтересу. Чеська: 2.1 на мільйон проти 4.5 рік тому,
−38 %/рік, довіра висока».

### 3.4 Запит №3 і уточнення — англійська у 4–5 розділах, PDF, `compare`
```bash
uv run scripts/wiki_interest.py analyze --topic "English language" --langs pl,cs,uk,de --months 24 --out runs/eng-24
uv run scripts/wiki_interest.py report  --run runs/eng-24 --title "Interest in English" --notes "…" --lang uk
uv run scripts/wiki_interest.py analyze --topic "English language" --langs pl,cs,uk,de,es --months 12 --out runs/eng-12
uv run scripts/wiki_interest.py compare --runs runs/eng-24 runs/eng-12
```
Що казати:
- «Українські читачі дають темі 107 на мільйон — у 2–3 рази більше, ніж інші розділи; усі розділи падають,
  тому рейтинг автоматично перемикається на обсяг і резюме це пояснює».
- «PDF — одна сторінка A4: таблиця, графік, вердикт, рекомендація агента, припущення й обмеження».
- «`compare` показує: при скороченні вікна до 12 місяців pl і cs «стабілізуються» (−10 → −2 %/рік), але
  довіра падає з high до low — це артефакт короткого вікна, і агент має так і сказати».

### 3.5 «Які теми ростуть?» — `discover`
```bash
uv run scripts/wiki_interest.py discover --lang uk --include "астроном|косм|планет|фізик|наук" --exclude "фільм" --sustained
```
Що казати: «Топ-1000 статей місяця проти того ж місяця рік тому, у частках уваги, без службових сторінок.
Топ-листи — це увага: новини, серіали, персони. Тому `--sustained` додає 24-місячний тренд і довіру для
кожного кандидата — і фільм із +600 % за місяць одразу відрізняється від теми зі стійким ростом».

### 3.6 Агент на дешевій моделі (30 секунд)
*Показати `eval/transcripts/claude-code-haiku/5-verify.md`.* «Це Haiku 4.5. На питання „а це не боти чи
тільки мобільні?“ вона сама викликала `verify` і відповіла: десктоп −45 %, мобільні −50 %, боти 32 %,
контрольна перевірка збігається, падіння швидше за весь uk-розділ — „це не боти, не мобільні й не помилка
даних“. Три виклики, 21 секунда. Усі шість сценаріїв — 2–4 виклики, 21–73 с. Той самий сценарій пройшов
і на безкоштовній моделі через OpenRouter — повільніше, але з тим самим результатом після двох правок
інструкцій».

## 6. Чому це працює і корисно — три речення для журі

1. **Дані, не інтонація.** Кожне число у відповіді — з `result.json`, кожен висновок має рівень довіри з
   переліком причин, а `verify` перевіряє його незалежними вимірами.
2. **Дешева модель справляється.** Haiku 4.5 проходить усі сценарії за 2–4 виклики інструментів; інструкції
   доводились по транскриптах, а не по відчуттях.
3. **Чесність до обмежень.** Відсутня стаття, боти, сезонність, поточний місяць, лаг публікації — усе
   названо в Checks/Limitations і потрапляє в PDF. Навичка каже «не знаю» там, де не знає.

## 8. Питання, які можуть поставити, і відповіді

**Чому «на мільйон переглядів розділу», а не сирі перегляди?**
Бо розділи різного розміру: en ≈ 8 млрд переглядів на місяць, uk ≈ 60–100 млн. Частка уваги знімає
розмір і ще й компенсує загальне падіння трафіку Wikipedia (у uk-розділі −25 %/рік — це видно в `verify`
як «базова лінія»).

**Як рахуєте ріст і чому «очищений»?**
OLS на `log(pm + ε)` по місяцях, анулізований. Піки — робастний z-score (медіана і MAD, поріг 3.5);
пікові місяці замінюються медіаною сусідів, і тренд перераховується. Заголовкове число — очищене, бо
одна новина не має видаватись за тренд. Сирий ріст теж є в JSON, а розрив між ними — одна з причин
низької довіри.

**Що таке confidence і чому саме такі пороги?**
Прапори: покриття вікна < 70 %, частка піків > 30 %, p-value монотонності > 0.1, розрив між сирим і
очищеним ростом > 25 п.п., менше 1000 переглядів → low; м'якші версії → medium. Пороги в одному місці й
задокументовані; калібрування на розмічених кейсах — пункт roadmap. p-value — permutation-тест Спірмена,
без SciPy.

**Чому не векторний/семантичний кеш промптів?**
Бо «accurate hit» і «схожість векторів» суперечать: «росте» і «падає» майже однакові вектори; час запиту
змінює правильну відповідь. Кешуємо на детермінованому рівні — відповіді API (URL) і, як наступний крок,
результати аналізу за канонічним ключем (теми, мови, абсолютне вікно, версія методики). Однакові ключі —
однакова відповідь за побудовою.

**Що робить навичка, коли статті немає в мові?**
Статус `MISSING`, кандидати пошуку показуються, але не використовуються; агенту прямо сказано: відсутність
статті ≠ відсутність інтересу. Користувач може підтвердити назву через `--titles`.

**Як обрана модель тестування? Чому не Haiku через OpenRouter?**
Ключ OpenRouter безкоштовного рівня повертає 402 для платних моделей. Завдання дозволяє безкоштовні
моделі — прогнав на Nemotron. Додатково зробив раннер через `claude -p`, щоб гнати Haiku 4.5 по
підписці: усі сценарії за 26–60 с. Обидва раннери дають однакові транскрипти й рубрику.

**Скільки викликів інструментів потрібно?**
Типово 1–3: `resolve` (якщо тема неоднозначна), `analyze`, за потреби `report`/`verify`. На Haiku це
3 виклики і ~30 с. Перший прогін безкоштовної моделі робив 7 — після правок інструкцій стало 2.

**Як масштабувати на 50 тем × 20 мов?**
Уже зараз: `--topics-file` + `--langs` — одна матриця, один `data.csv`. Далі по roadmap: кластери тем
через Wikidata P31/P279, дампи або Wikimedia Enterprise у Parquet + DuckDB, асинхронні запити, спільний
кеш (Redis/S3) для команди.

**Де межа корисності?**
Інтерес до статті ≠ готовність платити; перегляди залежать від існування й якості статті; фільтр ботів
неідеальний (тому є `verify`); мовний розділ ≠ країна; дані з 2015‑07. Усе це друкується в кожному
резюме і в PDF.

**Чому одна сторінка PDF і як гарантуєте?**
Бо «поділитися» означає одну сторінку. Текст рекомендації зменшується до 7 pt і обрізається; блок
припущень і обмежень не випадає ніколи. Тест з нотатками на 80 абзаців перевіряє, що сторінка одна.

**Що дав незалежний рев'ю?**
Два критичних (traceback на `cz`/`ua`; неповні дані місяця кешувались назавжди), п'ять важливих
(зміщення `log1p`, причини довіри не в резюме, ранжування при суцільному падінні, `--months 1`,
англійський футер в українському PDF). Усі виправлені, кожне — з тестом, що падав до виправлення.

**Що б зробили наступним?**
Калібрування порогів довіри на розмічених кейсах; спільний кеш результатів для команди; discover з
Wikidata-класами замість регулярних виразів; країни через `top-per-country`; change-point detection.

## 9. Roadmap (для останнього слайда)
1. Кластери тем (Wikidata P31/P279, категорії) замість однієї статті.
2. `discover` за класами Wikidata й категоріями, не лише за regex.
3. Дампи / Wikimedia Enterprise → Parquet + DuckDB; спільний кеш результатів (Redis/S3) із ключем за
   канонічним запитом і версією методики.
4. Країни (`top-per-country`), а не лише мови.
5. Change-point detection, STL-сезонність, прогноз з інтервалами.
6. Багатосторінкові звіти, HTML-дашборд, моніторинг з алертами.
7. Калібрування довіри на розмічених кейсах; рубрика eval сильнішою моделлю замість regex.
